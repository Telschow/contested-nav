# Limitations

**Purpose.** A single list of what this repository cannot do, why, and what
would be required to change it. Written so that a reader does not have to
discover any of this by running the code.

Every entry is ordered by how much it would change the conclusions.

---

## 1. Blocking limitations

These prevent the repository from supporting any operational, product, or
programme claim.

### L1 — No real sensor data

Everything is generated by a synthetic fixture: an analytic trajectory with the
filter initialised exactly at the truth.

**Consequence:** no number here is a field measurement. Bias stability, noise
spectra, temperature behaviour, vibration response, time sync, latency — none
are characterised, because there is no hardware involved.

**What it would take:** a real capture set, vendored or referenced, with ground
truth. The trajectory reader is already validated against a published benchmark
ATE, so the reader side is not the obstacle; the data is.

**VERIFIED BY REPOSITORY.**

### L2 — The documented failure is not fixed

Visual aiding under GNSS denial is badly overconfident: mean NEES 419.4 against
an expected 3, 2σ coverage 20.0%. The configuration ships disabled.

**Consequence:** the repository demonstrates a problem rather than solving it.

**What it would take:** implementing one of the established remedies —
observability-constrained EKF, first-estimate Jacobians, an invariant or
right-invariant error-state formulation, the Schmidt Kalman filter, or a
pose-graph backend. None is present. This is the highest-value next step and it
is not a research question, it is an implementation task.

**VERIFIED BY REPOSITORY** and **VERIFIED BY EXTERNAL SOURCE** — see
[S10](SOURCES.md#s10)–[S16](SOURCES.md#s16).

### L3 — No comparison against an established consistent estimator

The repository does not run OpenVINS, VINS-Mono, an invariant EKF, or any other
published consistent filter on the same scenes.

**Consequence:** the repository cannot show that its formulation is *worse* than
the state of the art, only that it is overconfident in isolation. Without a
baseline, the numbers characterise a configuration, not the field.

**What it would take:** a harness interface and one reference implementation.
OpenVINS is a reasonable first choice, and the synthetic scenes would need to be
exported in a format it accepts.

**VERIFIED BY REPOSITORY.**

### L4 — No formal integrity target

FDIR performs chi-square innovation gating and per-channel fault detection,
isolation and recovery.

**Consequence:** there is no protection level, no alert limit derived from a
risk model, no availability requirement, and no argument that a fault is
declared before it causes unacceptable navigation error. Receiver autonomous
integrity monitoring is an established field with its own requirements
machinery, and none of it is engaged.

**What it would take:** a specified integrity target, a derivation of alert
limits from it, and validation against a fault model with defined detection and
false-alarm probabilities.

**VERIFIED BY REPOSITORY** and **VERIFIED BY EXTERNAL SOURCE** — [S1](SOURCES.md#s1).

## 2. Material limitations

These do not block the repository, but they bound what its results mean.

### L5 — Synthetic scenes are not a distribution over reality

Eight scenes vary trajectory geometry over a 4.65× path-length range, holding
duration, sample rate and the exact `t=0` initial state fixed. All seven case
verdicts are stable across them.

**Consequence:** the claim that survives is "the anchor model is structurally
overconfident under visual aiding", not "this filter has X% error in
conditions Y". Nothing here bounds behaviour on real imagery, real camera
degradations, or real outage patterns.

**Not varied:** duration, outage start time, outage duration, sensor rate
configurations, motion classes beyond smooth analytic paths, lighting, motion
blur, rolling shutter, or calibration error.

**VERIFIED BY REPOSITORY.**

### L6 — No RF or adversary model

Interference is modelled as a clean binary outage. There is no jamming model, no
spoofing model, no partial degradation, no multipath, no interference
characterisation.

**Consequence:** the FDIR layer is evaluated against a far simpler input than it
would face. An adversary that produces *plausible but wrong* fixes is
substantially harder than an outage, and is not tested at all.

**ADR-0007** records the spoof-permanence problem — the detection signal that is
still missing — and is tracked but unimplemented.

**VERIFIED BY REPOSITORY.**

### L7 — FDIR detects but does not classify

The gate isolates a channel and reports how long it was out. It does not
distinguish multipath from spoofing from sensor degradation.

**Consequence:** an operator receives "this channel is faulty", not "this channel
is being spoofed". No response is selected on the operator's behalf.

**VERIFIED BY REPOSITORY.**

### L8 — No accelerometer-bias falsification experiment

The research baseline raises whether an accelerometer-bias fault is detectable
under GNSS denial, by injecting a bias and checking whether the innovation gate
catches it. This is not implemented.

**Consequence:** a specific hypothesis in the project's own research framing
remains untested. It is listed as open rather than quietly dropped.

**VERIFIED BY REPOSITORY.**

### L9 — Two tests skip without external data

The TUM VI regression tests require reference data that is deliberately not
vendored, and skip when it is absent.

**Consequence:** in a clean checkout, coverage of the trajectory reader is
asserted but not exercised against the published benchmark.

**VERIFIED BY REPOSITORY.**

### L10 — Not independent

The estimator, the synthetic generator, the evaluation metrics and the
benchmark configuration are all written by the same author.

**Consequence:** no adversarial review, and the risk of a shared conceptual
error across generator and estimator is real. The strongest available mitigation
is that the failure *contradicts* the code's intent — the filter is not
overconfident because of a mistake that favours it, but despite every design
choice the author made.

**AUTHOR-STATED.**

## 3. Minor limitations

- **No wall-clock budget.** The code is synchronous and offline. Nothing is
  measured against a timing requirement, and "real-time" is not claimed.
- **No packaging for deployment.** It is a library, with no container, no
  hardware abstraction, no real-time operating system support.
- **Figures carry a matplotlib version difference.** Regenerated figures show
  metadata drift. Deterministic run-to-run, but a reviewer diffing images sees
  noise.
- **Result JSON is gitignored.** Numbers are reproducible from committed code and
  configuration, not from committed outputs. A reader must run the code.
- **`similarity` alignment is implemented but unused in headline numbers**, so a
  scale-error result exists in the code and is not exercised by the benchmark.

**VERIFIED BY REPOSITORY.**

## 4. Claims that were removed rather than qualified

Recorded so the removal is auditable.

| Claim | Why removed |
|---|---|
| "The real fix is a pose graph" | Implies novelty in identifying the remedy. Pose graphs are one established option among several; the literature is cited instead. |
| "Multi-scene validation is still open" | Became false when the scene sweep was added. Replaced with a scoped statement of what the 8 scenes do and do not establish. |
| "Demonstrates robustness" | Replaced with the actual scope: 10 noise seeds, 8 scenes, 7 stable verdicts. |
| "State of the art" | No algorithmic contribution exists to support it. |
| "The numbers characterise a configuration" | True but read as a disclaimer rather than a scoping statement; rewritten to state what the sweeps do establish. |

**VERIFIED BY REPOSITORY.**

## 5. If you only read one section

Read L2 and L3 together. The repository shows a real, reproducible failure and
does not compare itself against the field that already solved it. That single
gap is what stands between this being a measurement artefact and being an
engineering contribution.
